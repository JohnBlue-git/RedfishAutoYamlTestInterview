Case study

Insyde Redfish Automated Test

A conformance-testing framework for a hardware vendor's Redfish schema, property, and action extensions — run against real, live BMC hardware, built as a small declarative engine on top of pytest, and largely built in collaboration with an AI pair.

What's here is the design story, the AI-assisted engineering process, and how the tool is used day to day. Overview

What it is

Automated conformance testing for a hardware vendor's extensions to Redfish — the industry-standard REST API server hardware exposes for power, thermal, storage, and firmware-update control — on OpenBMC-based server-management firmware. Every test runs against real, live hardware over HTTPS; there is no mock or simulated BMC anywhere in the suite, across two hardware generations spanning multiple CPU and GPU vendor platform configurations.

Motivation

Why it exists

DMTF, the standards body behind Redfish, publishes free, open-source validators — the Service Validator and the Interop Validator. Both are used here too, but neither can answer the question this project exists to answer, for two structural reasons:

  • The Service Validator is GET-only and treats a missing property as legal — the standard schema marks almost everything optional, so it can confirm "is what you returned well-formed?" but never "did you return it at all?". Vendor conformance is largely the second question: the vendor's own spec says a property shall exist, and a platform quietly omitting it is a real, recurring failure mode the validator simply cannot see.
  • The Interop Validator can express "this must exist," but its model stops at the property — it can say a property is writable without saying what a write must send, return, or reflect, and it has no way to express an ordered sequence of operations (create → verify → delete, poll a long-running task, reboot-and-wait).

Full capability-by-capability comparison, including two earlier generations of this suite itself: see Three generations below.

Day to day

How it's used

A single CLI wraps pytest; every flag or argument it doesn't recognize passes straight through, so the full native pytest vocabulary (-m, -k, -v, …) always stacks on top of it. (Illustrative — the entrypoint script itself isn't included in this excerpt.) 

# Full suite against the configured rig, terminal output
python3 run_tests.py

# Same, plus a self-contained HTML report
python3 run_tests.py --html

# One schema, filtered to one platform
python3 run_tests.py -m "<platform> and Chassis"

# A destructive action stays off by default no matter what's selected -
# it needs its own explicit, named opt-in
python3 run_tests.py --allow-bmc-reset tests/Manager/
That last pattern is a deliberate safety choice, not an afterthought: a handful of action categories (host power control, a full BMC reset, a BIOS password change, a UEFI secure-boot key change, …) each require their own --allow-<category> flag, independent of test selection entirely — so a marker expression alone can never trigger a factory reset.
Architecture

A pytest plugin, not a pytest replacement

End to end, this is what happens on a single test run:

1. CLI entrypointunrecognized flags/args pass straight through to pytest
2. pytest collectionwalks the test tree, hands each schema's file to a custom collection hook
3. a schema's test-definition fileparsed into a real pytest Collector/Item tree — pytest's own custom-collection mechanism, not a bespoke one
4. live BMC over HTTPSper-rig connection config + per-platform resource-topology data build every request — no mock/fixture BMC anywhere
5. pass/fail per test, one reportterminal output, or a self-contained HTML report

Zooming into steps 2–3: pytest's model is kept, not replaced. Every declarative construct becomes a real pytest object, reached through one of pytest's own hooks — never a bespoke one:

Declarative constructBecomespytest hook
a schema's test filea Collectorpytest_collect_file
a test case / a payload / a sequence stepan Itemitem.runtest()
a platform-applicability declarationa markeritem.setup()
a setup/teardown declarationa fixture-like hookitem.setup() / item.teardown()
a verification declarationan assertionraised inside runtest()

That's why anything that already understands pytest — -m, -k, exit codes, CI integration — keeps working unmodified; the declarative layer sits on top of pytest's model instead of beside it.

Spec explodes combinatorially; every copy rots independently.

Both options write if/switch logic in a medium that cannot execute it. Conditional logic belongs somewhere a machine evaluates it — the reason this moved to real code at all.

        assert response.status_code == 200

@pytest.mark.service
class TestFanGet(FanFixture):

Design

Design concepts worth naming

The three-way split

Every test's behavior is assembled from three independent layers that never overlap: which rig (connection info), what that hardware actually has (a per-platform resource inventory), and what the spec requires of it (compliance data, with per-platform-tier deltas merged automatically). Keeping these three separate is what lets the same test definition run unmodified against ten different physical machines.

Safety as a first-class, orthogonal gate

A small number of action categories — host power control, firmware update, a full reset, a password change, a secure-boot key change — are dangerous enough on real hardware that none run by default under any test-selection expression. Each needs its own explicit opt-in flag, independent of which tests were otherwise selected.

A finding is reported, not hidden

When live hardware genuinely doesn't do what the spec requires, the house style is to write the test as though it should pass, let it fail honestly, and record the finding rather than quietly loosening the check. A green report that hides a real firmware gap is worse than a red one that names it.

Process

Working with an AI on a design this size

How the engine above was actually built — the process, not the design covered so far. Written down because the method transferred better than any individual output did: the same loop produced the engine itself, dozens of schema migrations, and this documentation set — and it caught several mistakes a write-code-and-hope approach would have shipped.

The shape of the loop

idea
GRILLone question at a time, until the design is pinned down — decisions, including the ones that overrode the recommendation
SPECproblem statement, user stories, decisions frozen in writing
TICKETSvertical slices, each with acceptance criteria and its blockers
IMPLEMENTone ticket per session · verify live · commit
RECORDstatus-ledger entry + a design-history paragraph, in the same commit as the work
next ticket

The important property: each stage produces a durable artifact on disk. No stage depends on conversation memory surviving, which matters because a design this size spans many sessions and context windows.

Phase 1 — grill the design before any code

The single highest-leverage step, and the least obvious one. Before any code, the design was interrogated question by question — execution model, config format, setup/teardown scope, verification design, id grammar, file layout, step data passing, platform hierarchy, risk guarding, compliance tiering, reporting, migration strategy. One question at a time, each with a recommended answer, waiting for a decision before moving on.

"This spec is the synthesis of an extended grilling session … every decision point above reflects an explicit choice made during that session, including several where the chosen option was not the initially recommended one — e.g. one-file-per-schema config layout, sequences living inside the same file as the tests they sequence rather than a separate top-level directory, and the exact order of the platform-tier hierarchy."
Three core structural decisions went against the AI's recommendation — and they were right. Had the AI simply proposed a design and started building, all three would have gone the other way, and each would have been expensive to reverse once dozens of schemas depended on it.
  • One question at a time. A batch of five questions gets one skimmed answer.
  • Insist on a recommendation with each question. "What do you prefer?" wastes the AI's judgement; "here's my recommendation and why, do you agree?" surfaces reasoning you can push back on.
  • Facts are looked up, decisions are asked. Anything discoverable from the filesystem or the live rig shouldn't become a question.

Phase 2 — spec, then tickets

The spec captures the problem statement, the solution, user stories, and — most usefully — an Implementation Decisions section that freezes the grilling outcomes, plus an Out of Scope section so later sessions don't quietly expand the work.

The tickets break it into vertical slices: each one cuts a complete path through the design and is demoable on its own, rather than being a horizontal layer. The very first ticket is instructive — "reads a schema's test-definition file, finds a single test case, turns it into a real collected pytest Item, executes it against the live BMC, and shows up as a normal report row." That's the whole stack, for exactly one read operation. 

**What to build:** the end-to-end behaviour, from the user's perspective
**Blocked by:** other tickets, or "None - can start immediately"
**Status:** ready-for-agent

- [ ] Acceptance criterion 1
- [ ] Acceptance criterion 2
  • Sizing to one context window. A ticket that doesn't fit gets split. The engine took roughly 48 tickets in total.
  • Explicit blockers. So any session can pick up the frontier — any ticket whose blockers are all done — without re-deriving the order.

Phase 3 — implement one ticket at a time

One ticket per session, then commit. The verification discipline is what makes the output trustworthy, and in this project it is unusually strict for a specific reason: there is no mock BMC. Every test hits real, shared hardware.

  • Explore the live rig before trusting the existing code. Repeatedly, an older hand-written test's assumptions were simply wrong — see "What this caught" below.
  • A dry-run collection check is not proof. It catches structural/config mistakes, and nothing else.
  • Verify with the narrowest thing that proves it. One test, then the file, then the suite. A full-suite run on flaky shared hardware produces noise that buries the signal.
  • Run the engine's own self-test suite before committing any change to the engine itself. Roughly 200 tests against a synthetic sandbox — the only way to change the engine without a rig.
  • Confirm before anything hard to reverse. Deleting a resource the test didn't create, a reboot/factory-reset, toggling a live service, pushing.

Phase 4 — record what was learned, not just what was done

Three artifacts, updated in the same commit as the work rather than reconstructed later:

ArtifactHolds
a living status ledgerone row per ticket: status and what was actually found — including where the ticket's own premise turned out wrong
a running design-history narrativeone paragraph per ticket: the reasoning, so a future reader knows why a mechanism exists
the commit messagethe full account — what changed, what was measured, what was left undone and why

Record findings, don't fix them into invisibility. When the hardware is genuinely wrong, the house style is to write the test as though it worked, let it fail honestly, and comment the finding with enough detail to reproduce it.

Durable context: project memory and skills

Two mechanisms stop each session from rediscovering the same things: short, auto-loaded per-directory notes recording each area's conventions and traps, and checked-in project skills encoding verification discipline rather than personal preference:

SkillJob
single-test-case authoringadd one test case (or one step) to an existing schema's coverage
whole-schema migrationport a whole schema off the old style: explore the live rig → build → verify → clean up

The rule of thumb for what belongs in these: if you find yourself explaining the same thing a third time, write it down where the AI will read it automatically.

Rules that did the heavy lifting

  • Surface disagreement early, then defer. If the AI thinks the approach is wrong, it says so once, clearly — then does what was asked.
  • Corrections mid-task are normal. Several mechanisms reached their final shape only after three or four rounds of "no, do it this way" — one retry/drain design for a collection that renumbers its members on delete being the clearest case.
  • Verify claims about the code against the code. Names, line counts, "who calls this" — all checkable, so check rather than assert.
  • Say what wasn't done. Deferred work, unverified assumptions, and environment problems get stated plainly.

Grill the design before writing code — and expect to overrule the AI. Then write it down (spec → tickets), do one slice at a time, verify against reality rather than against your own expectations, and record what you learned in the same commit. The artifacts on disk, not the conversation, are what carry the work between sessions.
