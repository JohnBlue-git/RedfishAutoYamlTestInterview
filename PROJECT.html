Case study

Redfish Conformance Test Engine

A conformance-testing framework for a vendor's Redfish implementation, including its schema, property, and action extensions. It runs against real BMC hardware, is built as a small declarative engine on top of pytest, and was largely built in collaboration with an AI.

Documentation-only case study. No source code, test definitions, or product data are included — only the concepts behind the design and the AI-assisted process used to build it.

Background

What is Redfish?

Every data-center server has a BMC (Baseboard Management Controller): a small, separate computer on the motherboard that lets an administrator manage the server remotely — power it on or off, read temperatures and fan speeds, update firmware, manage user accounts — even when the main operating system is down. OpenBMC is a widely used open-source firmware stack for BMCs.

Redfish is the industry-standard API for talking to a BMC, published by the DMTF standards body as the modern replacement for the older IPMI protocol. It is a RESTful API — JSON over HTTPS — organised as a tree of resources: 

/redfish/v1/                 service root
├── Systems/                 the host computer: power state, boot, CPUs, memory
├── Chassis/                 physical enclosure: sensors, fans, power supplies
├── Managers/                the BMC itself: network, logs, reset
├── AccountService/          users and roles
└── UpdateService/           firmware updates

Each resource follows a published schema that defines its properties. A client reads with GET, changes settings with PATCH, creates and deletes with POST / DELETE, and triggers operations (such as a reset) by invoking actions. Hardware vendors may add their own OEM extensions on top of the standard schemas, and often publish their own spec saying which properties their platforms must support.

Overview

What it is

Automated conformance testing for a vendor's Redfish implementation on OpenBMC-based firmware: does the BMC actually implement what the standard and the vendor's spec require? It covers standard properties, vendor extensions, writes, and actions, across many hardware platforms. Every test runs against real hardware over HTTPS; there is no mock BMC.

The idea: tests are data, not code. Each Redfish schema gets one declarative YAML file; a small engine built as a pytest plugin turns it into ordinary pytest tests. Which rig, what that hardware has, and what the spec requires are kept as separate layers, so the same test runs unchanged on every platform.

Why automate it

Hundreds of checks per firmware build, on many platforms, can't be done by hand — and each property should be checked against the vendor spec every time, not against memory.

Why not off-the-shelf

DMTF's validators are read-only or never send a write. The vendor spec says properties must exist, and some must be written and invoked.

Why a third framework

An in-house keyword runner was hard to maintain; hand-written pytest was hard to scale. This one turns tests into data, with pytest still underneath.

# Illustrative: one CLI wraps pytest, so native options still work
python3 run_tests.py --html          # full suite + self-contained HTML report
python3 run_tests.py -m Chassis      # one schema
python3 run_tests.py -k ".GET"       # read-only tests
python3 run_tests.py --allow-bmc-reset tests/Manager/   # risky action: explicit opt-in

Architecture

A pytest plugin, not a pytest replacement

1. CLI wrapperunknown flags pass straight through to pytest
2. pytest collectiona custom hook reads each schema's YAML file and builds real pytest Collector / Item objects
3. live BMC over HTTPSrig connection + platform inventory feed each request — no mock BMC anywhere
4. one reporta row per test step; every request shown as a replayable curl command

Every declarative construct becomes a real pytest object, so everything that already understands pytest — -m, -k, exit codes, CI — keeps working, and old hand-written tests could run side by side during migration.

Comparison

Why not just the DMTF validators?

DMTF publishes free, authoritative validators. They are used too — but they answer a different question.

  • Service Validator is read-only and treats a missing property as legal, because the standard marks most properties optional. Vendor conformance asks the opposite: the vendor spec says a property shall exist.
  • Interop Validator can say "must exist", but never actually sends a write or invokes an action, and has no notion of an ordered sequence.
The division of labour: a pure-read resource with no vendor extension is the validator's job. Anything with a write, an action, a vendor extension, or a must-exist property belongs to this suite.
Design

Key design concepts

Tests are data

Tests say what; the engine decides how. One engine change upgrades every test with no test edits, and a Redfish-literate QA engineer can add coverage without knowing pytest.

The three-way split

Which rig, what that hardware has, and what the spec requires are independent layers — so one test runs unchanged on every platform, and a new platform is a data change.

Platform tiers

Applicability is declared against a tier hierarchy (common → chip generation → customer → platform). A new platform picks up every matching test automatically.

Expected, not discovered

The inventory says what a platform should have. A device it names but the BMC doesn't return is a failure, not silently skipped.

Sequences

Multi-step flows (create → verify → delete, reboot and wait) where each step is its own report row and values pass between steps.

Write, reflect, restore

Every write is re-read to prove it took effect, and the original value can be put back — shared rigs are left as found.

Safety as an orthogonal gate

Dangerous actions each need their own --allow-<category> flag, independent of test selection. A marker expression alone can never trigger a reset.

Report findings honestly

When hardware doesn't meet the spec, the test fails — it's never loosened to go green. A red row raises the question: is the firmware wrong, or the spec?

Process

Working with an AI on a design this size

Three loops, not a line

Feature loop      idea → /grill-me → /to-spec → /to-tickets → tickets on disk
Ticket loop       a ticket → /implement → verify live → /code-review → outcome
Improvement loop  a mistake or a correction → a rules line, a skill edit, or memory

Every stage produces a durable file on disk — nothing depends on conversation memory surviving across sessions.

  • Per-folder rules record each area's conventions and the traps already paid for.
  • Project skills (4) encode repeatable jobs with verification built in: writing a test case from a plain-language description or a curl command, onboarding a new platform, refreshing a platform's inventory from its live rig (read-only, each change adopted deliberately), and regenerating compliance data from the spec.
  • Skill adapters tell the global workflow skills where this repo keeps its tickets and docs.
  • Getting the same setup: cloning gives every in-git layer; a teammate adds the workflow skills, their own global rules (the author's four: think before coding, simplicity first, surgical changes, goal-driven execution), and lets memory build up.

Grill the design before any code

Before any code, the design was interrogated one question at a time, each with a recommended answer, waiting for a decision before moving on.

Three core structural decisions went against the AI's recommendation — and they were right. Had the AI simply proposed a design and started building, each would have been expensive to reverse.

Spec, then vertical-slice tickets

The spec freezes the decisions and an out-of-scope list. Tickets are vertical slices sized to one context window, with explicit blockers. The first ticket: read one YAML test case, turn it into a real pytest Item, run it against the live BMC, show it as a report row — the whole stack, for one read.

Three gates that keep it safe

There is no mock BMC — every test hits real, shared hardware.

Gate 1 — before a rig run

The user is the safeguard: read what the AI is about to send, and confirm anything hard to reverse.

Gate 2 — before claiming a pass

Show four things: the command, which rig, pytest's summary line copied exactly, the report file. A dry run, a smaller run than claimed, and skips are not passes. Where it matters, prove the check can fail.

Gate 3 — before committing

/code-review with two sub-agents — repo rules and the ticket, with any outside requirement passed in. A person reviews. Engine changes need the self-tests green.

A read-only audit of the engine

Once the engine had grown to about 4,800 lines across 14 modules, nobody had read it end to end — and its worst past bugs had all been silent: a check that verified nothing still reported PASS. So the same loop ran on the engine itself:

1. Grill the scoperanked: silent false passes, then docs drift, then self-test gaps
2. Audit read-onlyeach finding: claim, scenario, code-path evidence, proof — nothing changed
3. Maintainer decides59 findings: 55 accepted, 4 rejected
4. Tickets15, grouped by shared fix, through the normal gates
24 of the 26 tickets from the audit and its follow-ups are done, and the engine's self-test suite went from about 215 to 523 tests — each one pinning down behaviour that used to be unchecked.
